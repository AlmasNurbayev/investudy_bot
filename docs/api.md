# REST API (`cmd/api`)

Как устроен и почему так. Контракт — [api/openapi.yaml](../api/openapi.yaml),
решения и порядок работ — [plans/pnl-architecture.md](plans/pnl-architecture.md).

## Устройство

Демон на fiber v3, тот же образ и та же схема, что у бота: `db.NewPool`, штатный
`SIGTERM`. Слои: **handler → service → repository**. При старте все маршруты пишутся
в лог (`msg=route`, с пометкой `public` / `session` / `admin`).

## Остановка и таймауты

Только средствами fiber, без собственного учёта запросов: `Listener` в горутине, по
`SIGTERM` — `app.ShutdownWithTimeout(5s)`, и `Run` дожидается его. Он закрывает
приёмник, ждёт, пока запросы допишут ответы, и через 5 секунд рвёт оставшиеся
соединения. `main` закрывает пул только после этого. Без ожидания (`Listen`
возвращается, как только закрыт приёмник) `pool.Close` ждал висящий запрос 38 секунд —
дольше, чем Docker ждёт до `SIGKILL`.

**Контекст запроса.** `c.Context()` у fiber по умолчанию пустой и не отменяется —
запрос к базе не замечал бы ни остановки, ни таймаута. Поэтому первый middleware
кладёт в него контекст с таймаутом `DB_TIMEOUT`, производный от общего, который
отменяет хук `OnPreShutdown` (его fiber вызывает первым делом при остановке). Запрос,
висящий в базе, прерывается сразу (pgx отменяет его в Postgres), клиент получает 503;
истёкший таймаут — 504. Проверено на живой базе: остановка при запросе, повисшем
на блокировке таблицы, занимает полсекунды.

**Не использовать `c.RequestCtx()` как родителя** контекста: fasthttp отменяет его при
остановке сам, но его значения читает горутина отмены, пока fiber в них пишет —
детектор гонок (`-race`, он включён в CI) это ловит.

**Спекулятивные соединения.** fasthttp считает только что принятое соединение занятым
ещё 5 секунд. Браузер (и Go-клиент) иногда открывает лишнее соединение заранее и не
шлёт по нему запрос — остановка ждёт такое до конца `grace`, а потом закрывает
принудительно (в логе `соединения закрыты принудительно`). Это безвредно, но поэтому
тесты остановки ходят клиентом без keep-alive.

## Пакеты

- `api/openapi.yaml` — **контракт и единственный источник правды**. Сервер
  генерируется `oapi-codegen` (строгий интерфейс, `fiber-v3-server`) в
  `internal/api/oas/oas.gen.go` — руками не правится, после правки контракта
  `make generate`. Генератор подключён директивой `tool` в `go.mod`. Тот же файл
  вшит в бинарник (`api/embed.go`) и раздаётся Swagger UI на `/api/docs`.
- `internal/api` — транспорт: приложение, middleware сессии, ошибки.
- `internal/api/handler` — реализация интерфейса, DTO и **все тексты ответов**.
- `internal/auth` — пароли (argon2id, PHC), сессии, ограничение попыток входа.
- `internal/users` — заведение и правка пользователей: здесь проверки, которых
  нет в базе (роль, подразделение руководителя, способ входа, последний администратор).
- `internal/report` — выбор среза и ОПиУ (`Service.PnL`), общий с ботом.

## Доступ

**Закрыт по умолчанию.** Middleware сессии пропускает без cookie только
пути из списка `public` (`/api/auth/login`, `/healthz`, `/api/docs`, `/api/openapi.yaml`), остальное — 401. Документация открыта намеренно: контракт секретов не содержит, а страницы входа до SPA нет. Права
администратора проверяются **по префиксу `/api/admin/`** в том же middleware, а не в
обработчиках: новая админская ручка защищена тем, что легла под префикс.
Маршрутизация **строгая и чувствительная к регистру** (`CaseSensitive`,
`StrictRouting`): иначе `/API/admin/users` дошёл бы до ручки мимо проверки префикса —
это проверено тестом, и дыра была настоящей.

## Сессия и вход

`POST /api/auth/login` отвечает `200`: cookie в `Set-Cookie` и тело — то же, что у
`GET /api/me` (id, роль, username, подразделение с именем, `is_admin`, `has_report`,
`last_line`), чтобы после входа фронту не нужен второй запрос. Неверные логин и пароль,
несуществующий и заблокированный пользователь — один и тот же `401`; после пяти
неудач подряд — `429` с `Retry-After`.

Сессия — 32 случайных байта в cookie `session` (`HttpOnly`, `SameSite=Lax`,
`Secure` по `API_COOKIE_SECURE`), в базе только SHA-256. Скользящий срок 90 дней,
продление не чаще раза в 5 минут. Пользователь читается из базы на каждом запросе,
поэтому роль и подразделение действуют сразу; блокировка и смена пароля ещё и
удаляют сессии. Попытки входа — 5 неудач за 15 минут на пару «логин + адрес», в
памяти процесса (экземпляр один). Адрес клиента берётся из `X-Real-IP` только от
loopback и частных сетей — от своего nginx.

## Формат хеша пароля

В `users.password_hash` лежит строка в PHC-формате (argon2id), которую считает
`auth.HashPassword`:

```
$argon2id$v=19$m=65536,t=3,p=4$<соль>$<хеш>
```

| Часть        | Значение                                                              |
| ------------ | --------------------------------------------------------------------- |
| `argon2id`   | алгоритм                                                              |
| `v=19`       | версия argon2 (0x13)                                                  |
| `m=65536`    | память, КиБ (64 МиБ)                                                  |
| `t=3`        | число проходов                                                        |
| `p=4`        | параллелизм                                                           |
| `<соль>`     | 16 случайных байт, base64 **без** padding (`=`), алфавит `A-Za-z0-9+/` |
| `<хеш>`      | 32 байта результата, тот же base64                                    |

- **Секрет не нужен.** Хеш зависит только от пароля, соли и параметров; «перца» в
  окружении нет. Параметры лежат в самой строке, поэтому `VerifyPassword` читает их
  оттуда, а не из констант: их можно менять, не ломая уже выданные хеши.
- Соль случайная — один пароль даёт разные хеши, это нормально.
- Другой формат (bcrypt и т. п.) `VerifyPassword` отвергает ошибкой, вход не проходит.
- Минимальная длина пароля — 10 символов (`auth.MinPasswordLen`); проверяется при
  создании и смене через API, при ручной вставке в базу — нет.

Ручная вставка первого администратора (роль из списка `division_head`, `coo`, `cco`,
`founder`, `cfo`; `login` — строчными):

```sql
INSERT INTO users (login, password_hash, role, is_admin)
VALUES ('almas', '$argon2id$v=19$m=65536,t=3,p=4$…$…', 'cfo', true);
```

## Пользователи

Пользователей правит администратор, саморегистрации нет. Правка — `PUT` с
полным набором полей, а не `PATCH`: «не прислали» не путается с «очистили».
Пароль — отдельной ручкой `PUT /api/admin/users/{id}/password`, без старого пароля
(хеш руками не посчитать). Себя нельзя заблокировать и разжаловать, последнего
администратора — тоже; проверка идёт в транзакции под `FOR UPDATE` строк
администраторов. Первого администратора заводят вручную в базе: команды для этого нет.

## Отчёт

`GET /api/pnl?grain=month&cols=2026-03,2026-04&snapshot=` — не больше 12
колонок одной длины (`2026-03`, `2026-Q1`, `2026`), по умолчанию шесть месяцев по
текущий. Суммы — строками. Неразмеченные статьи — только администратору, остальным
флаг `incomplete`. Пользователь без действующей роли (`viewer` из старой таблицы
бота) входит, но отчёта не видит: `/api/me` отдаёт `has_report: false`.
