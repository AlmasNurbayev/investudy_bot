# Веб-ОПиУ: решения и открытые вопросы

Рабочий документ разговора от 06.09.2026. Первая часть — то, что решено;
вторая — вопросы, ждущие ответа. Структура самого отчёта лежит отдельно,
в [pnl-structure.md](../pnl-structure.md).

> **Частично заменён [pnl-architecture.md](pnl-architecture.md) (решения от 15.09.2026).**
> Где документы расходятся, главнее план: вход по логину и паролю, а не Telegram
> Login Widget; пять ролей и флаг администратора; отчёт через `GET`, а не `POST`;
> структура отчёта в базе. Строки ниже, которые устарели, помечены «→ план».

## Решено

| Вопрос | Решение |
| --- | --- |
| Что делаем | ОПиУ (отчёт о прибылях и убытках) по денежным операциям |
| Транспорт | Сайт: REST-бэкенд на Go + SPA на React |
| Судьба бота | Остаётся рядом. В боте — краткая выжимка ОПиУ, на сайте — подробно. → план: выжимка в боте отложена |
| Что умеет сайт | **Только чтение.** Правка проводок запрещена: источник правды — Google Sheets, и парсер перезатрёт любую правку |
| Вход | ~~Telegram Login Widget~~ → план: **логин и пароль**. `users` общая для бота и сайта, `telegram_id` — колонка, а не ключ |
| Срок сессии | → план: таблица сессий, скользящие 90 дней, вариант (б) из вопроса 6 |
| Раздача | React собирается в бандл, nginx отдаёт корень и статику, `/api` проксируется в Go |
| Колонка суммы | `sum_dash`. Проверено: она в точности равна `доход + расход + возврат`, расхождение 0.00 |
| Отбор разделов | **По статье (`item`)**, не по типу и виду. Обоснование — ниже |
| Колонки отчёта | По умолчанию последние 6 месяцев по `period`. Все колонки **одного размера периода** (только месяцы, только кварталы или только годы) — иначе сравнение некорректно. Колонки можно добавлять |
| Диаграмма на странице ОПиУ | Строится по тем же колонкам, что и таблица |
| Дашборд | Отдельная страница, свои диаграммы. → план: январь…текущий месяц этого и прошлого года, по компании, всем ролям |
| Роли | → план: руководитель отдела (до валовой, своё подразделение), опердир (до операционной), коммерческий (до чистой), учредитель и финдир (всё); администратор — отдельный флаг |
| Займы | В ОПиУ не входят |
| Фильтрация по ролям | На сервере. Клиент не получает того, что не должен показывать |

### Почему отбор по статье

Проверено на данных: у каждой из 13 статей **ровно один** вид и **ровно один**
тип — статья определяет их обоих однозначно.

За одно утро 06.09.2026 источник дважды переклассифицировал одни и те же
50 строк на −366 449 157 ₸: `дивиденды` переехали из типа `движение`
в `расход`, `займы` — из `доход` в `движение`. Отчёт на типе и виде изменил бы
чистую прибыль за 2026 год на **159.9 млн** без единой правки кода. Отбор
по статье этого не заметил.

## Открытые вопросы

### 1. Строка под дивидендами

За январь–август 2026 заработано 86.4 млн, распределено дивидендами
159.9 млн. Разница — **−73 513 764 ₸**, и у этой строки нет названия.

- (а) «Нераспределённая прибыль (убыток)» — итоговая строка отчёта
- (б) дивиденды последние, итога под ними нет
- (в) дивиденды справочно, вне арифметики

**Рекомендация: (а).** Если дивиденды стоят в столбце и не складываются,
читатель сложит их сам и получит число, которого в отчёте нет. Эта строка —
главная новость отчёта. Но цифру стоит проверить глазами: если она неверна,
неверен отбор, а не арифметика.

### 2. Куда `возврат прочих доходов`

Перечисляя низ отчёта («прочие расходы, прочие доходы, чистая прибыль,
дивиденды»), статью `возврат прочих доходов` не назвали. 5 строк, −29 860 ₸
по всей истории.

**Рекомендация: отдельный раздел, по аналогии с верхом.** Наверху
`возврат доходов` стоит своей строкой рядом с выручкой; низ должен быть
устроен так же.

### 3. Три статьи вне структуры

| Статья | Тип | Σ янв–авг 2026 | Особенность |
| --- | --- | ---: | --- |
| `инвест. доходы` | расход | +2 400 958 | тип «расход», сумма со знаком плюс |
| `инвест. расходы` | расход | −4 655 000 | |
| `сообщества доходы` | расход | 0 | тип «расход», +705 428 на истории |

Источник только что перевёл первые две в вид `прочая`.

**Рекомендация: оставить вне ОПиУ, показывать счётчиком.** Названия и типы
у них рассогласованы, и любой раздел, куда их положить, будет складывать
разнонаправленные числа.

### 4. Глубина раскрытия по разделам

В обсуждении прозвучало «раскрытия по `division, item`», но `item` теперь —
селектор самого раздела: внутри раздела статья одна, раскрывать по ней нечего.
Значит **подразделение → подстатья**?

Отдельно: у `админ. расходы` (32 подстатьи) и `общие налоги` (5 подстатей)
подразделение **ровно одно** — раскрывать по нему нечем.

**Рекомендация: глубина задаётся отдельно для каждого раздела**, колонкой
«Раскрытие» в [pnl-structure.md](../pnl-structure.md). Черновые значения там
проставлены. Единого правила не выйдет: данные разной формы.

### 5. Тип и вид в источнике; счётчик статей вне структуры

Для ОПиУ колонки «тип» и «вид» больше не нужны — статья определяет их обе.
Вопрос: убирать ли их из листа.

**Рекомендация: счётчик «статьи вне структуры» обязателен независимо от
этого решения.** Список разделов лежит в MD-файле и правится руками, а
справочник статей растёт в Google Sheets сам. Тринадцатая статья появится —
и без счётчика её деньги выпадут из отчёта молча, с заполненной суммой,
ровно как выпали бы сегодня дивиденды.

Колонки «тип» и «вид» стоит **оставить** как перекрёстную проверку: именно
их избыточность позволила доказать, что статья определяет классификацию
однозначно. Решение обратимое.

### 6. Срок сессии и отзыв доступа

Telegram Login Widget подписывает данные HMAC-ом от токена бота, но его
`auth_date` живёт минуты — это разовый вход. Срок сессии решаем мы.

- (а) долгая cookie (90 дней) + проверка `users` при каждом запросе
- (б) долгая cookie + таблица сессий (можно погасить конкретное устройство)
- (в) JWT на 90 дней без обращения к БД — отозвать нельзя
- (г) короткая сессия + refresh

**Рекомендация: (а).** Отзыв обязан работать: у отчёта пять читателей, и когда
один перестанет быть своим, удаление строки в `users` должно отрезать его
немедленно, а не через 90 дней. Вариант (в) это исключает в принципе.
Вариант (б) — если нужен «выйти на всех устройствах».
