# Веб-ОПиУ: предложения по архитектуре и структуре данных

## Context

docs/plans/pnl-web.md, docs/pnl-structure.md). Документы писались в разное время и

и предлагаемые архитектура и схема. Цель — закрыть вопросы до первой строки кода.

### Недельное ОПиУ

Что показали данные среза №4:

- **`type_oper = 2`** — «начисление для расчета месячного PL», датировано 1-м числом
  периода. Заполнено только в **открытых** месяцах (июль −22.4 млн, июнь −4.8 млн);
  в закрытых (май, апрель) суммы обнулены — начисление гасится, когда приходит факт.
- **`type_oper = 4`** — банк `virtual`, «с ОП на продукт»: перераспределение выручки
  и комиссий между подразделениями. По компании в ноль, **по подразделению — нет**
  (±7.4 млн). Для отчёта руководителя отдела это существенно.
- `period` — месяц, поэтому неделя может резаться только по `date`.

#### Как считается сейчас: лист «PL weekly» в «отчеты 2026»

Разобран по формулам 15.09.2026 (Sheets API, `valueRenderOption=FORMULA`).

- **Колонки** — недели пн–вс, обрезанные границами месяца: `01–04.01` (чт–вс, 4 дня),
  `31.08` (1 день). В шапке каждой недели: начало, конец, дней недели в месяце,
  дней в месяце, месяц.
- **Строка** — тройка «подразделение / статья / подстатья», перечисленная в листе руками.
- **Способ расчёта задан на строку и на неделю**: рядом с каждой суммой недели стоит
  метка. У `ВИ / произв. расходы / оплата услуг (ИП, ГПХ)` первые 30 недель
  `fact-day`, дальше `fact-month proportional` — отсюда срок действия правил.

Способы — справочник «периодичность затрат» в листе `lists`:

| Метка | Что считает формула | Ячеек |
|---|---|---:|
| `fact-day` | Σ дебет − Σ кредит, где дата ∈ неделе **и** период = месяц недели | 31 710 |
| `fact-month proportional` | Σ за **весь месяц** по периоду (все проводки: и факт, и начисления) × дней_недели / дней_месяца | 4 898 |
| `calc` | формула с коэффициентом, вбитая в ячейку | 88 |
| `budget-month proportional` | бюджет месяца × дни — из листа `import_plan`, которого в файле нет | 0 |

`calc`-строк две, коэффициенты одинаковы во всех 44 неделях:
- `отдел продаж / произв. расходы / оплата услуг (ИП, ГПХ)` =
  (выручка отдела продаж − комиссия банка отдела продаж + возвраты всех подразделений / 2) × 0,11
  — возвраты в листе отрицательные, то есть это «минус половина возвратов»;
- `руководство и общее / общие налоги / налоги и отчисления - КПН/ИПН/СН с оборота` =
  (выручка всех подразделений + возвраты) × 0,03.

**Метод один на строку и неделю** — `SWITCH` выбирает ровно одну ветку. Пропорция
заменяет факт недели, а не добавляется к нему. Поправка к прежней версии плана:
делится **вся сумма месяца**, а не только начисления `type_oper 2`.

#### Что в листе разъехалось — движок это не повторит

- **Отбор выручки** — по подстатье и подразделению, **без статьи и без периода**, а с
  недели 30.03 — ещё и без `type_oper 4`. Расходы — по всей тройке и периоду.
- **«3. Gross Profit»** до колонки BE вычитает расходы 3 подразделений из 8, входящих
  в «2. Operating Expenses», дальше — 4, в колонке BI — все. Формулы разъехались при копировании.
- **Строки перечислены руками**: проводка с новой тройкой в недельный отчёт не попадает.
  В месячном листе на это есть контрольная колонка «итог минус сумма строк», в недельном нет.

#### Решено

- Неделя пн–вс, обрезана границами месяца.
- Методы: **факт** (без правила), **пропорция месяца**, **коэффициент**; один на тройку и неделю.
- Коэффициент **заменяет** все суммы цели за неделю. База — все суммы шага 1, включая
  разнесённые пропорцией. Цепочек нет.
- У правил есть срок действия. Модель и порядок расчёта — §3.6.

Сумма недель месяца не совпадёт с месячным ОПиУ — свойство оперативного отчёта,
на странице недельного ОПиУ показать пометкой.

#### Осталось уточнить

1. **Структура недельного отчёта** — та же, что у месячного (разделы по статьям из
   pnl-structure.md)? В листе она другая: разделы по подразделениям, «8.1 отдел продукта -
   разработка», «8.2 Application development».
2. **Отбор факта** — один для всех строк: дата ∈ неделе **и** период = месяц недели,
   как у расходов в листе? Выручку лист берёт без периода.
3. **`type_oper 4`** (перераспределение между подразделениями) в недельном — учитывать,
   как в месячном, или исключать, как лист делает с выручкой с 30.03?
4. **Бюджетная пропорция** — бюджета в базе нет. Откладываем?
5. **Gross Profit в листе** вычитает расходы не всех подразделений — это намеренно?
   Движок вычтет весь раздел 1.3.

## 2. Архитектура

```
React SPA (Vite) ──► nginx ──/api──► cmd/api (fiber) ──► PostgreSQL ◄── cmd/parser
                       └── static                       ▲
                                              cmd/bot ──┘  (переиспользует internal/pnl)
```

**Новый бинарник `cmd/api`** — демон, тот же образ, та же схема, что у бота:
`db.NewPool`, штатный `SIGTERM`. Слои по конвенции проекта:

| Пакет | Роль |
|---|---|
| `internal/api` | fiber, маршруты, middleware сессии и роли |
| `internal/api/handler` | DTO, коды ошибок |
| `internal/auth` | пароли (argon2id), сессии, rate-limit входа |
| `internal/access` | политика: роль → cutoff строк + фильтр подразделения. **Одна функция** для API и бота |
| `internal/pnl` | движок ОПиУ: структура + агрегаты → дерево строк с итогами |
| `internal/repository` | SQL (добавить `PnlReader`, `UserStore`, `SessionStore`) |
| `internal/lib/period` | расширить: кварталы/годы уже есть по смыслу, добавить недели месяца |

Переиспользуются как есть: `internal/lib/snapshot.Latest` (рабочий срез + `Stale`),
`internal/lib/money`, `internal/db.NewPool`, `internal/config`, `internal/logger`.

**Контракт: OpenAPI-first вместо swag-аннотаций.** `api/openapi.yaml` → `oapi-codegen`
(умеет fiber, strict-server) на бэке и `openapi-typescript` на фронте. Swagger UI
раздаётся из того же файла. Так контракт — один источник правды для Go и TS, а не
комментарии, которые расходятся с кодом молча.

**Сессии: cookie `HttpOnly; Secure; SameSite=Lax`, same-origin через nginx** — CORS
не нужен, токен в JS не попадает. Случайный токен 32 байта, в БД — только его SHA-256.
Скользящий срок — настройка `settings.auth.session_ttl_days` (сид 90 дней); лимит входов, длина пароля и колонки отчёта — там же и в `settings.pnl`, см. docs/queries.md. Блокировка/смена пароля/смена роли удаляет сессии пользователя
— отзыв мгновенный (вариант (б) из pnl-web.md: он же даёт «выйти везде»).

**Фронтенд:** Vite + React + TS, TanStack Query (кэш по ключу срез+колонки),
TanStack Table (настраиваемые колонки и виртуализация для детальных данных),
React Router, графики — ECharts или Recharts. Состояние отчёта (гранулярность,
колонки, срез) — в URL: отчёт можно переслать ссылкой.

## 3. Структура данных

### 3.1 Структура ОПиУ — в базе, а не в MD

MD-файл нельзя ни проверить, ни отредактировать из админки. Таблицы дают то, что JSON
в `settings` не даст: **PRIMARY KEY по статье — «разделы не пересекаются» гарантирует
база**.

Статья привязывается **по имени, а не FK на `items`**. Две причины:
- статья попадает в `items` только с первой проводкой (`сообщества расходы` уже есть
  в листе `lists`, но фактов нет) — разметить её заранее через FK нельзя;
- сид лежит в миграции, а на свежей базе `items` пуста до первого прогона парсера.

Семантика от этого не меняется: парсер и так апсертит справочник по имени, поэтому
переименование в листе даёт новую статью в обоих вариантах — и она всплывёт в счётчике
неразмеченных. Сравнение по `lower(trim(name))`, как в `closed_reports`.

```sql
CREATE TABLE pnl_lines (
    id        SERIAL PRIMARY KEY,
    code      TEXT UNIQUE NOT NULL,          -- '1.1', '4'
    title     TEXT NOT NULL,
    kind      TEXT NOT NULL,                  -- 'section' | 'total'
    sort      INT  UNIQUE NOT NULL,           -- порядок сверху вниз
    expand    TEXT[] NOT NULL DEFAULT '{}'    -- '{division,sub_item}', только для section
);

-- Каждая статья: в разделе (line_id), исключена намеренно (line_id NULL)
-- или отсутствует здесь вовсе — тогда «не размечена» и попадает в счётчик.
-- Имя, а не FK: статья может быть размечена раньше, чем появится её первая проводка.
CREATE TABLE pnl_item_map (
    item_name TEXT PRIMARY KEY,               -- строчными, без пробелов по краям
    line_id   INT REFERENCES pnl_lines(id)
);

```

**Как читать.** Строки отчёта — `pnl_lines` в порядке `sort`:
- `section` — сумма `sum_dash` проводок, чья статья привязана к строке в `pnl_item_map`.
  `expand` — путь раскрытия: `{division,sub_item}` даёт «подразделение → подстатья»,
  `{}` — раздел одной суммой;
- `total` — нарастающая сумма всех `section` выше. Формулы нет, поэтому итог не может
  «забыть» раздел, как Gross Profit в листе;
- статья в `pnl_item_map` с `line_id NULL` — исключена намеренно, без строки — не размечена.

Граница доступа роли — «последняя видимая строка» (§3.3), фильтр руководителя
накладывается на `division_id` в запросе, до агрегации.

Сид из pnl-structure.md (фрагмент):

| sort | code | kind | title | expand | статьи в `pnl_item_map` |
|---:|---|---|---|---|---|
| 10 | 1.1 | section | Выручка от основной деятельности | `{division}` | доходы |
| 20 | 1.2 | section | Возвраты от основной деятельности | `{division}` | возврат доходов |
| 30 | 1.3 | section | Расходы от основной деятельности | `{division,sub_item}` | произв. расходы |
| 40 | 1 | total | Валовая прибыль | | |
| 50 | 2 | section | Административные расходы | `{sub_item}` | админ. расходы |
| … | | | | | |
| 170 | 8 | total | Нераспределённая прибыль | | |
| | | | | | перевод, пополнение, перевод на оператора, движение денег, займы → `line_id NULL` |

`sort` с шагом 10 — чтобы вставить строку, не перенумеровывая соседние.

Недельный отчёт использует ту же структуру; как считаются суммы недели — §3.6.

Итог не хранит формулу: `total` = сумма всех `section` с меньшим `sort`.
Сид структуры — единственный INSERT по образцу `000002` (`ON CONFLICT DO NOTHING`):
строки из pnl-structure.md, разделы с раскрытием, исключённые статьи (`line_id NULL`).
Позже `settings.closed_reports.excluded_items` выводится из `line_id IS NULL`.

### 3.2 Движок: один запрос, дерево — в Go

```sql
SELECT c.idx, d.item_id, d.division_id, d.sub_item_id, sum(d.sum_dash)
FROM data d
JOIN unnest($2::date[], $3::date[]) WITH ORDINALITY c(from_, to_, idx)
  ON d.period >= c.from_ AND d.period < c.to_
WHERE d.snapshot_id = $1
  AND ($4::int IS NULL OR d.division_id = $4)   -- фильтр руководителя
GROUP BY 1, 2, 3, 4
```

Колонки любой гранулярности — просто список полуинтервалов, запрос один на отчёт.
Результат — сотни–тысячи строк; `internal/pnl` раскладывает по `pnl_item_map`,
строит раскрытие по `expand`, считает итоги, обрезает по cutoff роли и отдаёт
неразмеченные статьи отдельным блоком. Движок — чистая функция над срезом строк,
тестируется без БД.

### 3.3 Пользователи и сессии

`users` сейчас пуста, её PK `telegram_id` — поэтому меняем без переноса данных:

```sql
users (
    id            BIGSERIAL PRIMARY KEY,
    login         TEXT UNIQUE,                 -- NULL — только бот
    password_hash TEXT,
    telegram_id   BIGINT UNIQUE,               -- NULL — только сайт
    username      TEXT,
    role          TEXT NOT NULL,               -- division_head|coo|cco|founder|cfo
    division_id   INT REFERENCES divisions(id),
    is_admin      BOOLEAN NOT NULL DEFAULT false,
    blocked_at    TIMESTAMPTZ,
    created_at, updated_at TIMESTAMPTZ NOT NULL DEFAULT now()
)

sessions (
    token_hash   BYTEA PRIMARY KEY,
    user_id      BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    created_at, last_seen_at, expires_at TIMESTAMPTZ NOT NULL,
    user_agent   TEXT
)
```

- Проверки — в Go, не в базе (правило миграций в CLAUDE.md). Сервис пользователей
  при создании и правке: роль из списка; `division_id` есть ровно у `division_head`;
  есть `login` или `telegram_id`; при `login` задан пароль. `access.For` повторно
  отвергает неизвестную роль и руководителя без подразделения при каждом запросе.
- Одна таблица на бота и сайт: заблокированный на сайте не должен читать отчёт в боте.
  Middleware бота (`UserAllowed`) переходит на `telegram_id AND blocked_at IS NULL`.
- `is_admin` отдельно от роли и выдаётся любому: право редактировать пользователей и
  настройки не связано с глубиной отчёта. Bootstrap первого админа —
  `TELEGRAM_ADMIN_ID` для бота и ручная вставка в `users` для сайта (отдельной команды нет).
- `is_admin` и `TELEGRAM_ADMIN_ID` не сливаются (решение 03.10.2026): оповещения парсера
  получает **только** `TELEGRAM_ADMIN_ID`, один человек. Рассылка всем `is_admin`
  требовала бы читать получателей из базы — о её падении узнать было бы некому.
- Роль → последняя видимая строка, **включительно** — **константа в `internal/access`**,
  не таблица: это логика, а не данные (`division_head` → `1` + фильтр подразделения,
  `coo` → `4`, `cco` → `6`, `founder`/`cfo` → всё). Граница — по `sort` строки, а не
  по коду: коды не упорядочены лексикографически.
- Дашборд — исключение из границы: ряды по компании видят все роли (решение п. 13).

### 3.4 Найдено в данных: иерархия подстатей недостоверна

`sub_items.name` уникально глобально, `item_id` — от последнего апсерта. **39 подстатей**
встречаются под несколькими статьями (`оплата труда (штат)` — в админ., произв.
и прочих расходах). Значит:
- каскадный фильтр «статья → подстатья» строить по парам
  `SELECT DISTINCT item_id, sub_item_id FROM data WHERE snapshot_id = $1`, а не по
  `sub_items.item_id`;
- раскрытие раздела по подстатье корректно — статья берётся из `data`;
- в миграции задокументировать, что `sub_items.item_id` — справочное поле.

### 3.5 Деньги в JSON — строками

`NUMERIC(17,2)` в JS `Number` на границе точности. Суммы — десятичные строки,
фронт форматирует и парсит только для графиков.

### 3.6 Недельное ОПиУ: правила расчёта (вычисляемые поля)

Разделы, итоги и раскрытие — те же `pnl_lines`, что у месячного. Отличается только,
**как получается сумма тройки «подразделение / статья / подстатья» за неделю**: её
метод берётся из правила, действующего на эту неделю. Это аналог метки `type` рядом
с каждой суммой в листе, только задаётся один раз с датами, а не в каждой ячейке.

```sql
CREATE TABLE pnl_weekly_rules (
    id            SERIAL PRIMARY KEY,
    -- Цель правила. '' = «любое значение».
    division_name TEXT NOT NULL DEFAULT '',
    item_name     TEXT NOT NULL,
    sub_item_name TEXT NOT NULL DEFAULT '',
    method        TEXT NOT NULL,               -- 'month_prorate' | 'calc'
    coef          NUMERIC(12,6),               -- только у calc
    valid_from    DATE NOT NULL,               -- включительно
    valid_to      DATE,                        -- не включительно; NULL — действует сейчас
    comment       TEXT,
    updated_by    BIGINT REFERENCES users(id),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now()
);

-- Слагаемые базы для calc: coef × Σ(weight × сумма отбора за неделю).
CREATE TABLE pnl_weekly_rule_terms (
    id            SERIAL PRIMARY KEY,
    rule_id       INT NOT NULL REFERENCES pnl_weekly_rules(id) ON DELETE CASCADE,
    division_name TEXT NOT NULL DEFAULT '',
    item_name     TEXT NOT NULL,
    sub_item_name TEXT NOT NULL DEFAULT '',
    weight        NUMERIC(12,6) NOT NULL DEFAULT 1
);
```

В базе — только ключи и `NOT NULL` (правило миграций в CLAUDE.md). Проверки правил —
чистая функция в `internal/pnl`, вызывается при сохранении (400 со списком нарушений)
и повторно при расчёте:
- `item_name` не пуст; `method` — `month_prorate` или `calc`; `coef` есть ровно у `calc`;
- цель `calc` — ровно одна тройка (подразделение и подстатья не `''`): иначе одно
  вычисленное число размножилось бы на все подходящие строки;
- `valid_to` позже `valid_from`;
- **непересечение**: для одной цели в каждый день действует не больше одного правила.
  Сохранение — в транзакции, которая сначала берёт `SELECT … FOR UPDATE` по правилам
  цели: две одновременные правки иначе прошли бы проверку каждая по отдельности.

Имена — нормализованные (`pnl.NormalizeItem`, как в `pnl_item_map`) и по той же
причине: правило на подстатью можно завести до её первой проводки.

**Смена правила не редактирует старое**, а закрывает его датой и заводит новое:
`[2026-01-01, 2026-08-03)` → `[2026-08-03, —)`. Прошлые недели пересчитываются
по правилам, действовавшим тогда, и отчёт за март завтра не изменится оттого, что
сегодня поменяли коэффициент. Правило недели выбирается по её первому дню.

#### Порядок расчёта недели W месяца M

Тройки берутся из данных среза плюс цели действующих `calc`-правил — вычисленная
строка есть, даже если проводок по ней за неделю не было.

1. **Шаг 1 — факт или пропорция.** Для тройки — самое узкое правило, действующее
   на начало W: подр.+статья+подст. → статья+подст. → подр.+статья → статья.
   - правила нет → **факт**: Σ `sum_dash`, `date ∈ W` и `period = M`;
   - `month_prorate` → Σ `sum_dash` за `period = M` (все проводки) × дней_W / дней_M.
2. **Шаг 2 — коэффициенты.** Для цели `calc` сумма шага 1 **заменяется** на
   `coef × Σ(weight × сумма шага 1 по отбору слагаемого)`. `''` в слагаемом — «все значения».
3. Дальше как в месячном: раскладка по `pnl_item_map`, раскрытие, итоги, граница роли.

**Цепочек нет**: отбор слагаемого не может пересекаться с целью `calc`-правила,
действующего в пересекающиеся даты (отборы с `''` пересекаются по смыслу, а не по
равенству). Проверяется там же, где остальные правила: при сохранении и при расчёте —
нарушение даёт ошибку, а не число.

Начисление `type_oper 2` без правила ложится в неделю своей даты (1-е число) —
отчёт показывает предупреждение, иначе месячная сумма молча уйдёт в первую неделю.

#### Правила из листа в этой модели

`sum_dash` знаковый: расходы и возвраты отрицательные. Поэтому `coef` у расхода
отрицательный, а «минус комиссия» — это слагаемое с весом `+1`.

| Цель (подразделение / статья / подстатья) | Метод | coef | Действует | Слагаемые (подразделение / статья / подстатья × weight) |
|---|---|---:|---|---|
| отдел продаж / произв. расходы / оплата услуг (ИП, ГПХ) | calc | −0.11 | с 01.01.2026 | отдел продаж / доходы / * × 1<br>отдел продаж / произв. расходы / комиссия банка, платежных сервисов × 1<br>* / возврат доходов / * × 0.5 |
| руководство и общее / общие налоги / налоги и отчисления - КПН/ИПН/СН с оборота | calc | −0.03 | с 01.01.2026 | * / доходы / * × 1<br>* / возврат доходов / * × 1 |
| ВИ / произв. расходы / оплата услуг (ИП, ГПХ) | month_prorate | | с недели, где в листе сменилась метка | |
| * / админ. расходы / оплата труда (штат) | month_prorate | | с 01.01.2026 | |

Проверка знаков на первой строке: лист — `+0,11 × (выручка − |комиссия| − |возвраты|/2)`,
положительный расход. База — `выручка + комиссия + 0,5 × возвраты` (два последних
отрицательны) = то же число; расход в `sum_dash` отрицательный → `coef = −0,11`.

**Перенос из листа** — разовой утилитой: метки `fact-month proportional` и `calc`
по строкам и неделям сворачиваются в правила с датами смены метки. 4 898 ячеек
пропорции дают порядка сотни правил; дальше их правит финдир в админке.

Выбор правила, свёртка меток и проверка цепочек — чистые функции в `internal/pnl`,
тестируются таблицами случаев без БД.

## 4. Контракт API (вместо списка из backend.md)

```
POST   /api/auth/login              {login, password} → Set-Cookie + тело как у /api/me
POST   /api/auth/logout
GET    /api/me                      роль, is_admin, видимые строки, подразделение

GET    /api/snapshots               селектор версии
GET    /api/pnl?grain=month&cols=2026-03,2026-04,…&snapshot=   ≤ 12 колонок, одна гранулярность
GET    /api/pnl/weekly?year=&month=&snapshot=
GET    /api/dashboard               помесячно янв…текущий месяц: этот год и прошлый, для 1.1+1.2, 4, 6
GET    /api/transactions?snapshot=&from=&to=&item=&sub_item=&division=&cursor=
GET    /api/transactions/export?format=xlsx|pdf&fields=…   те же отборы и та же политика доступа
GET    /api/dictionaries?snapshot=  статьи, пары статья–подстатья, подразделения

GET    /api/admin/users             POST /api/admin/users
PATCH  /api/admin/users/{id}        login, password, role, division_id, blocked
GET    /api/admin/pnl-structure     PUT — правка разделов и разметки статей
GET    /api/admin/unmapped-items
GET    /api/admin/weekly-rules      PUT — правила недельного ОПиУ, с проверкой цепочек
```

GET вместо `POST /api/pnl` из pnl-web.md: отчёт — чтение, его состояние должно жить в URL.

**Выгрузка генерируется на сервере**, а не в браузере: тем же запросом, что и таблица,
поэтому политика доступа применяется в одном месте и клиенту не нужно тянуть все
строки. XLSX — `excelize` в потоковом режиме (`StreamWriter`), память не растёт с
числом строк. PDF — выбранные колонки, все строки, альбомная ориентация, шапка
таблицы повторяется на каждой странице. Колонки, не влезающие в ширину листа,
переносятся на следующую полосу, а не сжимаются до нечитаемого шрифта.

Ответ `/api/pnl`:
```json
{ "snapshot": {"id": 4, "taken_at": "…", "stale": false},
  "columns": [{"key": "2026-08", "title": "Авг 2026", "from": "…", "to": "…"}],
  "lines": [{"code": "1.3", "title": "…", "kind": "section", "values": ["-410997534.00"],
             "children": [{"dim": "division", "id": 3, "name": "…", "values": [], "children": []}]}],
  "unmapped": [{"item": "…", "values": []}] }
```
`unmapped` видит только админ; остальным — флаг «отчёт неполный».
