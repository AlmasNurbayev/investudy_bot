# CLAUDE.md

Этот файл — инструкция для Claude Code (claude.ai/code) при работе с кодом репозитория.

## О проекте

Сервис для загрузки, хранения и отдачи финансовой информации.
Данные идут по цепочке Google Sheets → PostgreSQL → Telegram-бот (Go) и REST API.

Пять бинарников, один общий Docker-образ:

| Бинарник          | Роль                                         | Как живёт                         |
| ----------------- | -------------------------------------------- | --------------------------------- |
| **cmd/parser/**   | загрузка среза из Google Sheets в PostgreSQL | одноразовый, запускается кроном   |
| **cmd/migrator/** | миграции БД (golang-migrate)                 | одноразовый, стартует до сервисов |
| **cmd/prunedb/**  | чистка истории снепшотов (`-scheme monthly`) | одноразовый, запускается кроном   |
| **cmd/bot/**      | Telegram-бот, читает из PostgreSQL           | демон                             |
| **cmd/api/**      | REST API на fiber, читает из PostgreSQL      | демон                             |

SPA **ещё не написано**: решения приняты, кода нет. Всё, помеченное ниже как
«проектируется», описывает договорённости, а не состояние репозитория. `cmd/api`
написан (этап 4 плана): вход, `/api/me`, срезы, ОПиУ, админка пользователей.

## Архитектура

```
Google Sheets
     │  Sheets API v4 (REST + oauth2/jwt)
     ▼
cmd/parser        одноразовый: один срез → выход
     │
     ▼
PostgreSQL        единственный источник правды
     ▲   ▲
     │   └── cmd/prunedb   чистка истории по расписанию
     │
     ├── cmd/bot        Telegram-бот
     │        │
     │        ▼
     │   Telegram users
     │
     └── cmd/api        REST API
              ▲
              │  /api через nginx, same-origin
         React SPA (проектируется)
```

Бот и API читают одно и то же — `data` по разрешённому `snapshot_id` — и делят
движок ОПиУ (`internal/pnl`) и политику доступа (`internal/access`): два
разных ответа на один вопрос хуже, чем отсутствие второго канала.

### parser

Читает лист целиком, превращает строки в доменные структуры и публикует их одной транзакцией как новую версию среза. **Одноразовый**: расписание — на кроне, а не тикер внутри процесса, поэтому ненулевой код возврата служит сигналом о неудаче. Доступ — service account JSON, путь в env.

Официальный SDK `google.golang.org/api/sheets/v4` намеренно не используется: он линкует gRPC и OpenTelemetry (445 пакетов против 215), хотя Sheets API чисто REST-ный и нужен ровно один GET.

О каждом прогоне парсер пишет в Telegram **одному человеку — `TELEGRAM_ADMIN_ID`** (`internal/notify`), а не всем с `is_admin` (см. «Уровни доступа»): об удачном — номер среза, число загруженных строк и сколько из них **без обязательной аналитики** (подразделение, статья, период — по ним строятся все разрезы отчёта, и без любого из них проводка в отчёте невидима, хотя в базе лежит). Молчание иначе неотличимо от «крон не запустился». О падении — тем же каналом, и только потом выход с ненулевым кодом.

Тексты обоих сообщений лежат в `cmd/parser`, а `parser.Sync` возвращает `parser.Report` наружу вместо того, чтобы рассылать самому: так всё, что видит администратор, собрано в одном месте.

`Gaps.Rows` меньше суммы `NoDivision + NoItem + NoPeriod` — в одной строке обычно пусто сразу несколько полей. Разбор строки листа доезжает разложенным по полям — лист, номер строки, банк, организация, адрес ячейки (`W245`), заголовок колонки и её содержимое: чинить адресат пойдёт в Google Sheets, и ему нужно знать, куда смотреть. Носитель этих полей — `sheets.RowError`, `cmd/parser` достаёт его через `errors.As`. Библиотека `go-telegram/bot` для этого не берётся по той же причине, что и SDK Sheets: нужен ровно один POST `sendMessage`.

Другие особенности парсера — [docs/parser.md](docs/parser.md).

### bot

Telegram-бот на `go-telegram/bot` — демон, читает из PostgreSQL, stateless.
**Подробно — [docs/bot.md](docs/bot.md)**: меню команд и его области, reply-клавиатура,
доступ, устройство отчёта.

| Команда           | Что делает                                                              |
| ----------------- | ----------------------------------------------------------------------- |
| `/closed_reports` | Сводка по закрытым периодам: текущий/прошлый месяц и квартал, `division → item → sub_item` |

Не ломать при правке:

- Команды — одна таблица `commands` в `internal/bot/bot.go`: из неё и маршрутизация,
  и меню Telegram (`SetMyCommands` при старте). Новая команда — только туда.
- Доступ — middleware, а не хендлеры: белый список `users` (`blocked_at IS NULL`)
  плюс `TELEGRAM_ADMIN_ID`.
- Все тексты для пользователя — в `internal/bot/handler`.

### Веб-ОПиУ, API и фронтенд

Рядом с ботом появляются `cmd/api` (fiber) и SPA на React: отчёт о прибылях и убытках
по денежным операциям, дашборд, детальные данные с выгрузкой, админка. Решения —
**всё описано в [docs/plans/pnl-architecture.md](docs/plans/pnl-architecture.md)**:
схема данных (`pnl_lines`, `pnl_item_map`, `users`, `sessions`, правила недельного
расчёта), движок отчёта, контракт API и порядок работ. Требования к страницам —
[docs/frontend.md](docs/frontend.md), строки отчёта — [docs/pnl-structure.md](docs/pnl-structure.md).

Перед тем как писать сюда код, читать план: он же главнее более ранних
[docs/plans/pnl-web.md](docs/plans/pnl-web.md) и [docs/backend.md](docs/backend.md)
там, где они расходятся (вход по логину, а не Telegram Login Widget; отчёт через GET,
а не POST; структура отчёта в базе, а не в MD).

Сделано (этапы 1–4 плана): миграция `000003` — `users` на `id BIGSERIAL` с логином и
паролем (`telegram_id` осталась колонкой, бот проверяет `blocked_at IS NULL`),
`sessions`, `pnl_lines` и `pnl_item_map` с сидом; движок `internal/pnl` (чистая
функция `Build` над агрегатами `repository.Reader.PnlFacts`) и политика
`internal/access.For` — по одному экземпляру на оба канала; `cmd/api`. Дальше по
плану — SPA (этап 5).

### api

REST API на fiber v3 — демон, как бот. **Подробно — [docs/api.md](docs/api.md)**:
остановка и таймауты, сессии, пользователи, отчёт. Не ломать при правке:

- Контракт — `api/openapi.yaml`, сервер из него генерируется (`internal/api/oas`,
  руками не правится): после правки контракта — `make generate`.
- Доступ закрыт по умолчанию: без сессии — только пути из `public` в
  `internal/api/server.go`; права администратора — по префиксу `/api/admin/`.
  Маршрутизация строгая и чувствительная к регистру — иначе префикс обходится.
- Тексты ответов — в `internal/api/handler`; проверки пользователей, которых нет
  в базе, — в `internal/users`.

### База данных

Драйвер — `pgx` (`github.com/jackc/pgx/v5`). Миграции — `golang-migrate/migrate` с pgx-драйвером; они **вшиты в бинарник мигратора** через `go:embed` (`migrate/embed.go`), поэтому копировать каталог в образ не нужно и бинарник не может разъехаться с миграциями. Файлы в `migrate/` в формате `000001_name.up.sql` / `000001_name.down.sql`.

Требования к миграциям:

- **Только DDL.** Никаких `TRUNCATE`, `UPDATE`, `DELETE` — миграция не трогает данные. Исключение — сиды справочных строк: `settings` (`000002`) и структура ОПиУ (`pnl_lines`, `pnl_item_map`). `INSERT … ON CONFLICT DO NOTHING` ничего не портит и не затирает отредактированное значение, а дефолт константой в Go дал бы два расходящихся источника правды у одного списка.
- **Без логики в базе.** Только таблицы, индексы, `PRIMARY KEY`, `UNIQUE`, `NOT NULL`, внешние ключи и `DEFAULT`. Никаких `CHECK`, `EXCLUDE`, триггеров, хранимых процедур и `DO`-блоков. Допустимые значения, связи между полями, непересечение интервалов проверяет Go — и при сохранении, и там, где данные читаются в расчёт (`pnl.Structure.Validate`, `access.For`).
- **Таблица, созданная в одной миграции, дальше меняется только через `ALTER`.** Никаких `DROP TABLE` + `CREATE TABLE` ради новой формы — ни в `up`, ни в `down`: в таблице могут быть данные боевого стенда (так `000003` переделывает `users` из `000002` на месте). Откат тоже возвращает форму через `ALTER`.
- **Идемпотентность** — многократный запуск не должен портить данные (`CREATE TABLE IF NOT EXISTS`, `DROP … IF EXISTS`). `ALTER` повторно не прогоняется: второй запуск обязан упасть ошибкой, ничего не изменив, а не потерять данные.
- Объекты, связанные обязательным (`NOT NULL`) FK, создаются в одной миграции: иначе `ADD COLUMN NOT NULL` упрётся в требование пустой таблицы.

**Таблица `data` версионируется снепшотами — перед написанием любых запросов к ней читать [docs/data-versioning.md](docs/data-versioning.md).** Кратко: у каждой строки есть `snapshot_id` → `snapshots(id)`, поэтому запрос без фильтра по версии вернёт все срезы разом и задвоит суммы.

Читающий код обращается к `data` **только через разрешённый `snapshot_id`** — он обязательный параметр каждого метода `repository.Reader`, забыть его невозможно. Какая версия рабочая, решает `internal/lib/snapshot`: новейшая **непустая**. Вью `data_current` для этого не годится — она прибита к новейшему срезу по `taken_at` безусловно, и пустой прогон парсера превратил бы отчёт в «данных нет» при живых вчерашних. Что показана не самая свежая версия, пользователь видит в шапке отчёта.

`data_current` остаётся для ручных запросов из [docs/queries.md](docs/queries.md).

Глубину истории держит `cmd/prunedb`: схема `monthly` оставляет все срезы за последние 30 дней и по одному, новейшему, за каждый предшествующий месяц.

История версионирования в ./docs/data-versioning.md

**`sub_items.item_id` — справочное поле, строить по нему фильтры нельзя.** Имя
подстатьи уникально глобально, а `item_id` остаётся от последнего апсерта: 39 подстатей
встречаются под несколькими статьями (`оплата труда (штат)` — и в админ., и в произв.,
и в прочих расходах). Пары «статья → подстатья» берутся из самих проводок:
`SELECT DISTINCT item_id, sub_item_id FROM data WHERE snapshot_id = $1`. Раскрытие
раздела по подстатье от этого не страдает — статья там тоже из `data`.

**Таймзона — `Asia/Almaty`**, зашита в двух местах, которые обязаны совпадать: `timezone` в `pg_conf/postgresql.conf` и generated-колонки `snapshots.year/month/week` в миграции. UTC здесь не годится: Алматы это UTC+5, поэтому ночной прогон кроном в UTC уехал бы на предыдущие сутки — срез, снятый в понедельник в 03:00, попал бы в воскресную неделю, а снятый 1 марта — в февраль.

Код на зону не завязан вовсе: `prunedb` группирует по готовым колонкам `year`/`month`, а не считает границу месяца сам. Поэтому граница в отчёте и в удалении одна по построению, и синхронизировать нечего.

### Уровни доступа

Роль задаёт **последнюю видимую строку ОПиУ, включительно** — колонка «Видна до» в
[docs/pnl-structure.md](docs/pnl-structure.md):

| Роль                            | Видит до строки     | Подразделения |
| ------------------------------- | ------------------- | ------------- |
| руководитель отдела             | 1 (валовая прибыль) | только своё   |
| операционный директор           | 4 (операционная)    | все           |
| коммерческий директор           | 6 (чистая прибыль)  | все           |
| учредитель, финансовый директор | всё                 | все           |

Администратор — **отдельный флаг `is_admin`**, а не роль: право заводить пользователей и
править настройки не связано с глубиной отчёта и выдаётся любому.

**`is_admin` и `TELEGRAM_ADMIN_ID` — разные вещи, и это решение, а не недоделка.**
`is_admin` — права в админке сайта (пользователей может быть несколько).
`TELEGRAM_ADMIN_ID` — **один человек**, технический ответственный: только он получает
оповещения парсера (удачные и неудачные прогоны) и пускается в бота без строки в
`users`. Оповещения не рассылаются всем `is_admin`: список получателей пришлось бы
читать из базы, а о падении самой базы тогда узнать было бы некому. Иметь `is_admin`
в `users` ему не обязательно, и наоборот — `is_admin` оповещений не получает.

Политика живёт **одной функцией в `internal/access`** и вызывается и API, и ботом: две
копии границы разойдутся молча, а цена расхождения — финансовые данные не тому читателю.

Исключения и детали (руководитель видит свой разрез целиком, включая перераспределение
между подразделениями; дашборд по компании виден всем ролям) — §1 и §3.3
[плана](docs/plans/pnl-architecture.md).

## Переменные окружения

Все переменные хранятся в едином `.env` в корне репозитория. Разбор — `caarlos0/env` по тегам структур (`internal/config`), недостающие переменные сообщаются одним списком.

| Переменная                | Назначение                                             |
| ------------------------- | ------------------------------------------------------ |
| `SPREADSHEET_ID`          | ID документа Google Sheets                             |
| `SHEET_NAME`              | Название листа (например, `ДДС`)                       |
| `GOOGLE_CREDENTIALS`      | Ключ service account: JSON или его base64              |
| `GOOGLE_CREDENTIALS_FILE` | Путь к service account JSON (альтернатива)             |
| `POSTGRES_HOST`           | Хост PostgreSQL                                        |
| `POSTGRES_PORT`           | Порт PostgreSQL                                        |
| `POSTGRES_DB`             | Имя базы данных                                        |
| `POSTGRES_USER`           | Пользователь                                           |
| `POSTGRES_PASSWORD`       | Пароль                                                 |
| `DB_TIMEOUT`              | Таймаут подключения и запросов (`30s`)                 |
| `MIN_PERIOD`              | Нижняя граница загрузки, `ДД.ММ.ГГГГ` (необязательная) |
| `TELEGRAM_BOT_TOKEN`      | Токен от @BotFather                                    |
| `TELEGRAM_ADMIN_ID`       | Telegram-id **единственного** получателя оповещений парсера |
| `API_ADDR`                | Адрес REST API (`:8080`)                               |
| `API_COOKIE_SECURE`       | `Secure` у cookie сессии (`true`; `false` — только локально по http) |

Расписаний в конфиге нет: `parser` и `prunedb` одноразовые, их запускает крон. Схема чистки — флаг `prunedb -scheme`, а не переменная: это параметр запуска, а не настройка среды.

`cmd/api` читает конфиг через `config.LoadAPI()`: `POSTGRES_*`, `DB_TIMEOUT`, `API_ADDR`, `API_COOKIE_SECURE`. Доступы к Sheets и Telegram ему не нужны. Домена cookie нет намеренно: сайт same-origin через nginx, и cookie без `Domain` привязана к своему хосту.

Мигратору и `prunedb` нужны только `POSTGRES_*` и `DB_TIMEOUT` — они читают конфиг через `config.LoadPostgres()`, а не через `Load()`, чтобы не требовать доступов к Sheets.

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_ID` обязательны и для парсера: он пишет администратору о неудачной загрузке. Получатель ровно один — тот, чей id в переменной; пользователи с `is_admin` оповещений не получают. Обязательны намеренно — грузить данные, не имея канала для жалобы, хуже, чем не стартовать: о падениях тогда никто не узнает до первого расхождения в отчёте.

Ключ сервис-аккаунта задаётся **ровно одним** из двух способов, и это проверяется при старте: оба разом — ошибка, а не «одно перекрывает другое». Два ключа в конфиге означают, что правили не тот, и молчаливый выбор победителя увёл бы парсер в чужую таблицу.

`GOOGLE_CREDENTIALS` несёт сам ключ, поэтому контейнеру не нужен bind-mount ради одного файла, а секрет едет тем же путём, что пароль базы и токен бота. Значение — голый JSON (в .env он ложится одной строкой: переносы внутри `private_key` экранированы самим форматом) или его base64. В базе есть только `A-Za-z0-9+/=`, поэтому через `include .env` в make, `env_file` в compose и шелл он проходит без сюрпризов, а JSON везёт кавычки и обратные слэши, которые разборщики теряют по-разному. Различаются они по первому символу: JSON ключа всегда объект, с `{` base64 объекта начаться не может.

`GOOGLE_CREDENTIALS_FILE` остаётся для запуска на своей машине — там ключ уже лежит файлом, и перекладывать его в `.env` ради одного прогона незачем.

`MIN_PERIOD` разбирается в формате самого листа (`01.01.2025`), а не RFC3339: в `.env` её пишет человек, который смотрит в колонку «Период». Для этого в конфиге заведён тип `config.SheetDate` — голый `time.Time` разбирался бы через `encoding.TextUnmarshaler`, то есть требовал бы `2025-01-01T00:00:00Z`.

`TZ=Asia/Almaty` задаётся не в `.env`, а в `docker-compose.yml`: это настройка контейнера. **Без кавычек** — `TZ='Asia/Almaty'` в YAML-списке попадёт в значение вместе с кавычками, имя зоны станет невалидным и молча откатится на UTC.

## Разработка (make)

```bash
make help              # список целей
make dev-parser        # один прогон парсера
make dev-api           # REST API локально (cookie без Secure)
make create-admin LOGIN=almas   # первый администратор сайта
make generate          # сервер из api/openapi.yaml
make migrate-up        # накатить миграции
make migrate-down      # откатить последнюю
make prune             # чистка истории (SCHEME=monthly)
make build             # бинарники в _bin/
make test              # тесты без БД (интеграционные пропускаются)
make test-integration TEST_DATABASE_URL=postgres://...   # тесты с БД
make lint / vet / fmt
make check             # fmt + vet + lint + test
make up / down / ps / logs   # стенд из docker-compose.yml в корне
```

`Makefile` подхватывает `.env` автоматически. Две неочевидности зафиксированы прямо в нём:

- `TEST_DATABASE_URL` **не выводится** из `.env` — интеграционные тесты начинают с `TRUNCATE`, и прогон против боевой базы стёр бы данные. Адрес указывается явно. `repository` и `api` чистят одну базу, поэтому их `TestMain` берёт advisory-блокировку Postgres на весь прогон пакета (`internal/testdb`): пакеты идут по очереди при любом запуске — `make`, CI, IDE. Без неё `go test ./...` в CI падал: один пакет стирал пользователей посреди теста другого.
- Цели форматирования перечисляют каталоги, а не `.`: обход всего репозитория спотыкается на `_volume_db` (файлы базы, root, 0700).

## Раскладка модуля

Один Go-модуль, `cmd/` + `internal/` (не `go.work`, не отдельные модули на сервис).

```
investudy_bot/
├── cmd/
│   ├── parser/        # загрузка среза
```

## Источник данных

Лист **ДДС** — банковские проводки, 24 колонки → таблица `data`. Аналитика

## Ключевые архитектурные решения

- Все бинарники в одном Docker-образе — упрощает сборку и деплой; конкретный сервис выбирается через `command`.
- Один Go-модуль вместо `go.work` с модулем на сервис: пакеты и так общие, а workspace добавлял бы церемоний без выгоды.
- PostgreSQL — единственный источник правды; парсер единственный пишет в `data`, бот и API только читают. Сайт правит пользователей, структуру ОПиУ и правила недельного расчёта — то, чего в листе нет; проводки не правит никто, следующий прогон парсера перезатёр бы правку.
- Отчёт и политика доступа — по одному экземпляру на оба канала (`internal/pnl`, `internal/access`): вторая копия границы доступа разойдётся с первой молча.
- Зависимости передаются через интерфейсы — репозитории и внешние клиенты описываются интерфейсом **в пакете-потребителе**, конкретная реализация передаётся через конструктор.
- О сбоях парсер сообщает администратору сам, а не полагается на разбор логов крона: цепочка Sheets → PostgreSQL молчаливая, и незамеченная неудачная загрузка выглядит как «данные почему-то вчерашние».
- Google Sheets credentials никогда не коммитятся — env-переменная указывает на файл вне репозитория; `.dockerignore` дополнительно исключает `.env` и `*.json` из контекста сборки.
- Каталоги, начинающиеся с `_`, — рабочие (`_volume_db`, `_bin`), исключены и из git, и из контекста Docker.
- Структура ОПиУ и правила недельного расчёта живут в базе, а не в константах Go и не в MD: их правит финансовый директор из админки. База держит только ключи (`PRIMARY KEY` по статье — разделы не пересекаются), остальную непротиворечивость проверяет Go при сохранении и повторно при расчёте.
- Публикация среза атомарна за счёт MVCC: строка `snapshots` и строки `data` создаются в одной транзакции, поэтому флаг «готовности» не нужен — недостроенная версия невидима другим сессиям до `COMMIT`.
