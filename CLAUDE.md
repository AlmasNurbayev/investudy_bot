# CLAUDE.md

Этот файл — инструкция для Claude Code (claude.ai/code) при работе с кодом репозитория.

## О проекте

Telegram-бот, отдающий пользователям финансовую информацию. Данные идут по цепочке Google Sheets → PostgreSQL → Telegram-бот (Go).

Четыре бинарника, один общий Docker-образ:

| Бинарник | Роль | Как живёт |
| --- | --- | --- |
| **cmd/parser/** | загрузка среза из Google Sheets в PostgreSQL | одноразовый, запускается кроном |
| **cmd/migrator/** | миграции БД (golang-migrate) | одноразовый, стартует до сервисов |
| **cmd/prunedb/** | чистка истории снепшотов (`-scheme monthly`) | одноразовый, запускается кроном |
| **cmd/bot/** | Telegram-бот, читает из PostgreSQL | демон |

## Архитектура

```
Google Sheets
     │  Sheets API v4 (REST + oauth2/jwt)
     ▼
cmd/parser        одноразовый: один срез → выход
     │
     ▼
PostgreSQL        единственный источник правды
     ▲   ▲
     │   └── cmd/prunedb   чистка истории по расписанию
     │
cmd/bot           читает только вью data_current
     │
     ▼
Telegram users
```

### parser

Читает лист целиком, превращает строки в доменные структуры и публикует их одной транзакцией как новую версию среза. **Одноразовый**: расписание — на кроне, а не тикер внутри процесса, поэтому ненулевой код возврата служит сигналом о неудаче. Доступ — service account JSON, путь в env.

Официальный SDK `google.golang.org/api/sheets/v4` намеренно не используется: он линкует gRPC и OpenTelemetry (445 пакетов против 215), хотя Sheets API чисто REST-ный и нужен ровно один GET.

О каждом прогоне парсер пишет администратору в Telegram (`internal/notify`): об удачном — номер среза, число загруженных строк и сколько из них **без обязательной аналитики** (подразделение, статья, период — по ним строятся все разрезы отчёта, и без любого из них проводка в отчёте невидима, хотя в базе лежит). Молчание иначе неотличимо от «крон не запустился». О падении — тем же каналом, и только потом выход с ненулевым кодом.

Тексты обоих сообщений лежат в `cmd/parser`, а `parser.Sync` возвращает `parser.Report` наружу вместо того, чтобы рассылать самому: так всё, что видит администратор, собрано в одном месте.

`Gaps.Rows` меньше суммы `NoDivision + NoItem + NoPeriod` — в одной строке обычно пусто сразу несколько полей. Разбор строки листа доезжает разложенным по полям — лист, номер строки, банк, организация, адрес ячейки (`W245`), заголовок колонки и её содержимое: чинить адресат пойдёт в Google Sheets, и ему нужно знать, куда смотреть. Носитель этих полей — `sheets.RowError`, `cmd/parser` достаёт его через `errors.As`. Библиотека `go-telegram/bot` для этого не берётся по той же причине, что и SDK Sheets: нужен ровно один POST `sendMessage`.

Другие особенности парсера - ./docs/parser.md

### bot

Telegram-бот на `github.com/go-telegram/bot`. Регистрация хендлеров через `bot.RegisterHandler`, запуск через `b.Start(ctx)`. Обрабатывает команды пользователей, читает из PostgreSQL, отправляет ответы. Stateless — всё состояние в БД.

Единственный демон среди бинарников: `Run` блокируется до отмены контекста, а не отрабатывает один прогон. Отсюда два отличия от парсера — соединение берётся из `db.NewPool` (за `db.Conn` один `*pgx.Conn`, а он не выдерживает конкурентных апдейтов), и штатная остановка по `SIGTERM` ошибкой не считается.

Слои: **handler → service → repository**.

- `internal/bot` — транспорт: запуск, маршрутизация, проверка доступа.
- `internal/bot/handler` — обработчики команд и **все тексты для пользователя**, включая форматирование таблицы. Тексты живут здесь по той же причине, по которой сообщения администратору лежат в `cmd/parser`: всё, что видит человек, собрано в одном месте, а сервис отдаёт данные.
- `internal/report` — сервис: выбор версии среза, настройки, итоги.
- `internal/repository` — SQL.

**Меню команд** бот публикует сам при каждом старте (`SetMyCommands`) — в две области, `all_private_chats` и `default`. Список команд хранится на стороне Telegram и переживает перевыкладку, поэтому заведённое когда-то через BotFather остаётся в меню, даже если бот этих команд не понимает; `SetMyCommands` заменяет список целиком, так что лишнее исчезает само. Источник списка один — таблица `commands` в `internal/bot/bot.go`, из неё же идёт регистрация хендлеров: иначе меню и маршрутизация разъезжаются молча. Имя команды в них пишется по-разному — `RegisterHandler` ждёт `/name`, `SetMyCommands` отвергает ведущую косую черту.

Две области — не перестраховка. Telegram берёт **первый установленный** список в порядке от узкого к широкому: `chat`+язык → `chat` → `all_private_chats`+язык → `all_private_chats` → `default`+язык → `default` ([алгоритм](https://core.telegram.org/bots/api#botcommandscope)). Публикация в одну только `default` — последняя в очереди, её перекрывает что угодно выше, включая список под конкретный язык клиента и включая **пустой**: меню тогда выглядит пустым, а публикация молча не действует, без ошибки в логе. `all_private_chats` выигрывает у обеих `default`-записей и покрывает личные чаты, где ботом и пользуются.

Диагностика, если меню не такое, как ждали, — спросить у Telegram, что у него лежит в каждой области (`getMyCommands` с `scope` и `language_code`); ответ `[]` означает «не установлено», непустой — что эта область перекрывает нижние.

**Reply-клавиатура** боту не нужна — он работает инлайн-кнопками, — но она хранится **на клиенте для конкретного чата** и переживает смену бота: кнопки, поставленные предыдущей версией под тем же токеном, остаются внизу экрана навсегда, пока их не снимут явно. Поэтому каждое сообщение без инлайн-разметки уходит с `ReplyKeyboardRemove` (`handler.orRemoveKeyboard`): на сообщение приходится один `reply_markup`, так что прицепить снятие можно только туда, где своей клавиатуры нет.

**Доступ** проверяется middleware, а не внутри хендлеров: забыть проверку в новой команде слишком легко, а цена забывчивости — финансовые данные постороннему. Белый список — таблица `users`; `TELEGRAM_ADMIN_ID` пускается всегда и в таблице быть не обязан, иначе сразу после миграции выдать доступ первому пользователю было бы некому. Выдача — SQL из [docs/queries.md](docs/queries.md).

#### /closed_reports

Сводка по закрытым периодам: кнопки «текущий/прошлый месяц», «текущий/прошлый квартал», разрезы `division → item → sub_item`, суммы `debet`/`credit`. Границы периода считает `internal/lib/period` (полуинтервал `[From, To)`, отсчёт от первого числа — `AddDate` по произвольному дню нормализует 31 марта минус месяц в 3 марта). Период отсекается по колонке `period`, а не `date`: «закрытый период» — понятие учётное.

Исключаемые статьи (`пополнение`, `перевод`, …) лежат в `settings` под ключом `closed_reports` — это внутреннее движение денег, и без отсечения каждая такая проводка задваивает итог. Отсутствие строки — громкая ошибка, а не пустой список: неверная сводка выглядит исправной.

Разметка ответа смешанная и это осознанно: заголовки и итоги — форматированный текст, он переносится по ширине экрана; строки таблицы — `<pre>`, потому что только моноширинный блок держит колонки и, в отличие от `<code>`, прокручивается вбок вместо переноса. Названия справочников приезжают из Google Sheets, поэтому тело таблицы экранируется целиком. Отчёт, не влезший в лимит Telegram, режется на сообщения по границам подразделений, с повтором заголовка — обрезать его нельзя: недостающие строки ничем себя не выдают, а итог просто не сойдётся.

### База данных

Драйвер — `pgx` (`github.com/jackc/pgx/v5`). Миграции — `golang-migrate/migrate` с pgx-драйвером; они **вшиты в бинарник мигратора** через `go:embed` (`migrate/embed.go`), поэтому копировать каталог в образ не нужно и бинарник не может разъехаться с миграциями. Файлы в `migrate/` в формате `000001_name.up.sql` / `000001_name.down.sql`.

Требования к миграциям:

- **Только DDL.** Никаких `TRUNCATE`, `UPDATE`, `DELETE` — миграция не трогает данные. Единственное исключение — сид строки в `settings` (`000002`): `INSERT … ON CONFLICT DO NOTHING` ничего не портит и не затирает отредактированное значение, а дефолт константой в Go дал бы два расходящихся источника правды у одного списка.
- **Идемпотентность** — многократный запуск не должен портить данные (`CREATE TABLE IF NOT EXISTS`, `DROP … IF EXISTS`).
- Объекты, связанные обязательным (`NOT NULL`) FK, создаются в одной миграции: иначе `ADD COLUMN NOT NULL` упрётся в требование пустой таблицы.

**Таблица `data` версионируется снепшотами — перед написанием любых запросов к ней читать [docs/data-versioning.md](docs/data-versioning.md).** Кратко: у каждой строки есть `snapshot_id` → `snapshots(id)`, поэтому запрос без фильтра по версии вернёт все срезы разом и задвоит суммы.

Читающий код обращается к `data` **только через разрешённый `snapshot_id`** — он обязательный параметр каждого метода `repository.Reader`, забыть его невозможно. Какая версия рабочая, решает `internal/lib/snapshot`: новейшая **непустая**. Вью `data_current` для этого не годится — она прибита к новейшему срезу по `taken_at` безусловно, и пустой прогон парсера превратил бы отчёт в «данных нет» при живых вчерашних. Что показана не самая свежая версия, пользователь видит в шапке отчёта.

`data_current` остаётся для ручных запросов из [docs/queries.md](docs/queries.md).

Глубину истории держит `cmd/prunedb`: схема `monthly` оставляет все срезы за последние 30 дней и по одному, новейшему, за каждый предшествующий месяц.

История версионирования в ./docs/data-versioning.md

**Таймзона — `Asia/Almaty`**, зашита в двух местах, которые обязаны совпадать: `timezone` в `pg_conf/postgresql.conf` и generated-колонки `snapshots.year/month/week` в миграции. UTC здесь не годится: Алматы это UTC+5, поэтому ночной прогон кроном в UTC уехал бы на предыдущие сутки — срез, снятый в понедельник в 03:00, попал бы в воскресную неделю, а снятый 1 марта — в февраль.

Код на зону не завязан вовсе: `prunedb` группирует по готовым колонкам `year`/`month`, а не считает границу месяца сам. Поэтому граница в отчёте и в удалении одна по построению, и синхронизировать нечего.

## Переменные окружения

Все переменные хранятся в едином `.env` в корне репозитория. Разбор — `caarlos0/env` по тегам структур (`internal/config`), недостающие переменные сообщаются одним списком.

| Переменная                | Назначение                                    |
| ------------------------- | --------------------------------------------- |
| `SPREADSHEET_ID`          | ID документа Google Sheets                    |
| `SHEET_NAME`              | Название листа (например, `ДДС`)              |
| `GOOGLE_CREDENTIALS_FILE` | Путь к service account JSON                   |
| `POSTGRES_HOST`           | Хост PostgreSQL                               |
| `POSTGRES_PORT`           | Порт PostgreSQL                               |
| `POSTGRES_DB`             | Имя базы данных                               |
| `POSTGRES_USER`           | Пользователь                                  |
| `POSTGRES_PASSWORD`       | Пароль                                        |
| `DB_TIMEOUT`              | Таймаут подключения и запросов (`30s`)        |
| `MIN_PERIOD`              | Нижняя граница загрузки, `ДД.ММ.ГГГГ` (необязательная) |
| `TELEGRAM_BOT_TOKEN`      | Токен от @BotFather                           |
| `TELEGRAM_ADMIN_ID`       | Telegram-id получателя оповещений о сбоях     |

Расписаний в конфиге нет: `parser` и `prunedb` одноразовые, их запускает крон. Схема чистки — флаг `prunedb -scheme`, а не переменная: это параметр запуска, а не настройка среды.

Мигратору и `prunedb` нужны только `POSTGRES_*` и `DB_TIMEOUT` — они читают конфиг через `config.LoadPostgres()`, а не через `Load()`, чтобы не требовать доступов к Sheets.

`TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_ID` обязательны и для парсера: он пишет администратору о неудачной загрузке. Обязательны намеренно — грузить данные, не имея канала для жалобы, хуже, чем не стартовать: о падениях тогда никто не узнает до первого расхождения в отчёте.

`MIN_PERIOD` разбирается в формате самого листа (`01.01.2025`), а не RFC3339: в `.env` её пишет человек, который смотрит в колонку «Период». Для этого в конфиге заведён тип `config.SheetDate` — голый `time.Time` разбирался бы через `encoding.TextUnmarshaler`, то есть требовал бы `2025-01-01T00:00:00Z`.

`TZ=Asia/Almaty` задаётся не в `.env`, а в `docker-compose.yml`: это настройка контейнера. **Без кавычек** — `TZ='Asia/Almaty'` в YAML-списке попадёт в значение вместе с кавычками, имя зоны станет невалидным и молча откатится на UTC.

## Разработка (make)

```bash
make help              # список целей
make dev-parser        # один прогон парсера
make migrate-up        # накатить миграции
make migrate-down      # откатить последнюю
make prune             # чистка истории (SCHEME=monthly)
make build             # бинарники в _bin/
make test              # тесты без БД (интеграционные пропускаются)
make test-integration TEST_DATABASE_URL=postgres://...   # тесты с БД
make lint / vet / fmt
make check             # fmt + vet + lint + test
make up / down / ps / logs   # стенд из docker-compose.yml в корне
```

`Makefile` подхватывает `.env` автоматически. Две неочевидности зафиксированы прямо в нём:

- `TEST_DATABASE_URL` **не выводится** из `.env` — интеграционные тесты начинают с `TRUNCATE`, и прогон против боевой базы стёр бы данные. Адрес указывается явно.
- Цели форматирования перечисляют каталоги, а не `.`: обход всего репозитория спотыкается на `_volume_db` (файлы базы, root, 0700).

## Структура источника данных (Google Sheets → PostgreSQL)

Лист **ДДС** (движение денежных средств) — банковские транзакции. 24 колонки:

| Поле (англ.)   | Русское название    | Тип / формат                                                |
| -------------- | ------------------- | ----------------------------------------------------------- |
| `date`         | Дата                | `DD.MM.YYYY`                                                |
| `numOper`      | #                   | строка                                                      |
| `typeOper`     | Тип                 | строка                                                      |
| `debetVal`     | Дебет валюта        | decimal                                                     |
| `creditVal`    | Кредит валюта       | decimal                                                     |
| `exRate`       | Курс                | decimal                                                     |
| `debet`        | Дебет               | decimal, запятая как разделитель; исключает `credit`        |
| `credit`       | Кредит              | decimal, запятая как разделитель; исключает `debet`         |
| `sender`       | Бенеф-р/отправитель | контрагент + ИИН/БИН                                        |
| `description`  | Назначение платежа  | свободный текст                                             |
| `bank`         | Банк                | короткое имя (`Kaspi`, `Halyk`, …)                          |
| `period`       | Период              | `01.MM.YYYY` — первое число месяца                          |
| `organization` | Организация         | юр. лицо (`Aligee`)                                         |
| `division_id`  | Подразделение       | FK → `divisions(id)`                                        |
| `item_id`      | Статья              | FK → `items(id)`                                            |
| `sub_item_id`  | Подстатья           | FK → `sub_items(id)` (sub_items.item_id → items)            |
| `comment1`     | Учет                |                                                             |
| `comment2`     | Комментарий         |                                                             |
| `fin_type_id`  | Тип                 | FK → `fin_types(id)` (`доход` / `расход` / `возврат` и др.) |
| `sumDash`      | СуммаДаш            | decimal                                                     |
| `vid_id`       | Вид                 | FK → `vids(id)` (центр затрат)                              |
| `sumRevenue`   | СуммаДоход          | decimal; заполнен только для `type=доход`                   |
| `sumCost`      | СуммаРасход         | decimal; заполнен только для `type=расход`                  |
| `sumReturn`    | СуммаВозврат        | decimal; заполнен только для `type=возврат`                 |

**Справочные таблицы:** `divisions`, `items`, `sub_items`, `fin_types`, `vids` — все FK nullable. Парсер апсертит значение по имени и получает id перед вставкой в `data`. Для `sub_items` сначала upsert родительского `item`, затем `sub_item` с `item_id`.

Апсерт пишется как `INSERT … ON CONFLICT (name) DO UPDATE SET name = EXCLUDED.name RETURNING id`, а **не** через `DO NOTHING RETURNING id`: последний на конфликте не возвращает ни одной строки, то есть для уже существующего значения id не придёт. Строк в справочниках десятки, лишняя запись роли не играет.

Особенности парсинга: в файле /.docs/parser.md

## Ключевые архитектурные решения

- Все бинарники в одном Docker-образе — упрощает сборку и деплой; конкретный сервис выбирается через `command`.
- Один Go-модуль вместо `go.work` с модулем на сервис: пакеты и так общие, а workspace добавлял бы церемоний без выгоды.
- PostgreSQL — единственный источник правды; парсер единственный пишет, бот только читает.
- Зависимости передаются через интерфейсы — репозитории и внешние клиенты описываются интерфейсом **в пакете-потребителе**, конкретная реализация передаётся через конструктор.
- О сбоях парсер сообщает администратору сам, а не полагается на разбор логов крона: цепочка Sheets → PostgreSQL молчаливая, и незамеченная неудачная загрузка выглядит как «данные почему-то вчерашние».
- Google Sheets credentials никогда не коммитятся — env-переменная указывает на файл вне репозитория; `.dockerignore` дополнительно исключает `.env` и `*.json` из контекста сборки.
- Каталоги, начинающиеся с `_`, — рабочие (`_volume_db`, `_bin`), исключены и из git, и из контекста Docker.
- Публикация среза атомарна за счёт MVCC: строка `snapshots` и строки `data` создаются в одной транзакции, поэтому флаг «готовности» не нужен — недостроенная версия невидима другим сессиям до `COMMIT`.
